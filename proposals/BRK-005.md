## The proposal (one sentence)
A proposal unanswered by the Owner for 2 consecutive Owner sessions auto-becomes
"HELD — expired," filed as such in proposals/, never silently ignored — the Omega-5 rule
applied to the proposal inbox (arc-protocol.md:30-38).

## Mechanics (all mechanical, no Owner field filled)
1. proposals/ gains a machine-readable header line per file: `expiry: {2 sessions | none}`.
2. On the breaker sweep / supervisor sweep (round 7 discipline), any proposal whose
   `filed` date precedes 2 Owner-controlled sessions and whose `Owner ruling` line is
   still `{...}` empty → append a `HELD — expired {date}` line to the file (append-only,
   never editing the body).
3. The expiry has ONE legal effect: the proposal may not be CITED as a live ask in any
   subsequent ruling; it may be re-filed fresh (new ID) with the old file cited as parent.
4. Exemptions: Owner-filed proposals, and any proposal carrying an explicit Owner line
   "HELD — active" (renewed).

## Dissent summary
- Seat III (Tomorrow): 2 sessions may be too aggressive for a slow-moving Owner —
  answered: the rule is about VISIBILITY (nothing silently dies; the file is filed as
  HELD-expired), not deletion; re-filing is one file copy + new ID. Cost of being too
  aggressive: LOW. Cost of too lax: the undead inbox returns (arc-protocol's own
  finding).
- Seat I (Consistency): what counts as an "Owner session"? — answered mechanically: any
  session in which the Owner wrote at least one line in the workspace's chat/log that day;
  counting games are a violation for the ledger, never silently fixed.

## Wrong-decision cost
- Adopt: an unanswered proposal becomes VISIBLE-dead instead of undead-invisible.
  Wrong-now cost: LOW (nothing is deleted; re-filing is trivial).
- Reject: the inbox keeps undead asks that never receive a ruling — the exact zombie
  ARC names. Cost: MEDIUM (institutional drift; the record fills with never-ruled
  proposals whose status is unknowable).
