## The proposal (one sentence)
Adopt the candidate definition: GFR ≥ 50% without contradictions (C=0) across 4 dims,
sustained over 3 tasks — as the DEFAULT reading of the breakthrough field, Owner-editable
or rejectable in one line.

## Candidate (proposed — the Owner owns the final numbers)
```
BREAKTHROUGH-CANDIDATE ≡ GFR ≥ 50% ∧ C = 0 ∧ min_3-task-window GFR ≥ 50% ∧ Y = 4 dims
GFR = S/D where D = Σ budgeted squares (S + C + U), S = filled WF(K) squares, C = contradictions
C  = squares flagged by (a) R10 sweep collision or (b) mic-23 re-run FAIL against claimed G=PASS
```
- Why these defaults: 50% is a beatable-but-honest first bar for a newborn grid (the
  first 3 tasks will fill less; the Z=3 window at 50% proves sustainability, not hype);
  Y=4 is the K-line's 4 fields (templates/DS.md:27) — every square already requires all 4
  under WF (breaker-measure.md:§1), so Y=4 is structural, not arbitrary.
- The Owner may write any of: X%, Y, Z, α, β (as BRK-002's frame + BRK-003's tiers).
  A rejection in one line ("threshold = ___") supersedes this file.

## Wrong-decision cost

  clause and the 3-task minimum. Cost: LOW.
- Reject-too-high (say 90%): the grid never reaches it in 3 tasks → breakthrough never
  landable → the metric reads "the system can never succeed" (the R10-freeze failure of
  canon-trial item 2, breaker-canon-trial.md:§2). Cost: MEDIUM.
- Reject outright: the Owner keeps his field as "text-until-then" (RATIFICATION-BATCH

  defer the VALUE to real-data time.
